# ntfy Desk: notes for agents

Browser extension (WXT 0.21, TypeScript, MV3 for Chrome and Firefox) to send and receive ntfy notifications. User-facing docs: `README.md`. How it works and why (receiving, storage, security model, why not WebSockets): `ARCHITECTURE.md`; update it when the design changes.

The public website (`https://ntfy-desk.minddevops.eu`) is in `website/`: read `website/AGENTS.md` before changing it, and update its pages when a feature they describe changes.

## Commands

- `pnpm check`: format check, lint with type checking, and Vitest. Run it before every commit; `pnpm fmt` fixes formatting.
- Lint and format come from Vite+ (`vp lint`, `vp fmt`; settings in `vite.config.ts`, used only by Vite+). Oxlint runs with type-aware rules and the full type check (`typeCheck`), strict with `noUncheckedIndexedAccess`; warnings fail. `pnpm compile` runs `tsc --noEmit` on its own. Markdown isn't formatted.
- `pnpm build` / `pnpm build:firefox`: `.output/chrome-mv3`, `.output/firefox-mv3`.
- `pnpm zip` / `pnpm zip:firefox`: the release zips. `pnpm verify:packages` (`scripts/validate-packages.ts`) checks them against the checkout: manifests (version, name, permissions, Firefox id), license notices, no stray files, source maps or E2E hooks, sources identical to the repository. Its expected permissions (`EXTENSION`) are written out, not read from `wxt.config.ts`: change a permission in both, and its justification in `assets/store-listings/` (a unit test compares them).
- `pnpm website:build`: the website, into `.output/website` (`website/README.md`). `pnpm check` builds it too, in `tests/unit/website.test.ts`.
- WXT takes the extension version from `package.json`. Verify both generated manifests when changing it.
- `pnpm lint:firefox`: builds for Firefox, then runs Mozilla's add-on checks (`web-ext lint`); CI runs them too.
- CI (`.github/workflows/ci.yml`): read-only token, nothing written to the repository (the `website` job deploys the site once `CLOUDFLARE_ACCOUNT_ID` is set; `website-preview.yml` uploads pull request previews, `website/README.md`), runs on pushes to `main` and pull requests (a tag starts no workflow); actions pinned to commit SHAs with the version in a comment, updated by Dependabot (`.github/dependabot.yml`). Keep new actions pinned the same way.
- Releases (`docs/releasing.md`): the manually started `.github/workflows/prepare-release.yml` builds and validates the packages without secrets, then, in the `release` environment, validates them again from a fresh checkout, signs the Chromium ZIP as a CRX when `assets/store-listings/chrome-web-store/crx-signing-public-key.pem` is committed (`scripts/sign-chrome.ts`, `docs/crx-signing.md`; skipped otherwise) and creates or refreshes a **draft** release; an existing draft keeps its title and notes. Publishing the draft is manual. Store submissions (`docs/store-publishing.md`): the first by hand; later ones through the manually started `.github/workflows/publish-stores.yml`, which downloads a published release's files, verifies them (`scripts/publish-stores.ts verify`) and, only with its `submit` input, uploads them in the `store-chrome` and `store-firefox` environments (main only; credentials are environment secrets, the Chrome ids repository variables). `scripts/validate-packages.ts`, `sign-chrome.ts`, `crx3.ts` and `publish-stores.ts` import only Node built-ins, since the signing and store jobs install nothing: keep it that way. Never dispatch either workflow, publish a release, create a tag or submit to a store unless the user asks, and never create, read or store the signing key or the store credentials. Store text lives in `assets/store-listings/` and must stay true to the code and `PRIVACY.md`.
- `pnpm dev` opens a browser with hot reload. For manual Chromium testing, load `.output/chrome-mv3` unpacked after `pnpm build`.
- `pnpm test:e2e` builds into `.output/chrome-mv3-e2e` and runs `tests/e2e/` in Playwright's Chromium against `tests/e2e/ntfy-server.ts`. The HTTP test server uses ntfy's JSON stream and accepts credentials only in the Authorization header; it records the publish headers (`published`) and holds delayed messages back (`scheduled`). Run one Chromium at a time. CI runs the same tests. The E2E build lets Playwright call the actual notification-click handler from the service worker. It covers the credential approval button in Settings. The E2E build also exposes the command handler (`__ntfyRunCommand`), since Playwright can't press a browser-level extension shortcut. Unit tests cover the optional host-permission request, which uses a Chromium prompt outside the page. Firefox runtime testing is separate.
- `pnpm browse [--headed]`: builds, then opens the extension's page in `playwright-cli` (mise tool) and prints the extension id. Then drive it with `playwright-cli snapshot`, `click <ref>`, `fill <ref> <text>`, `screenshot`, `close`; output lands in `.playwright-cli/`. Use it to look at UI changes in the real extension rather than a mocked page. `playwright-cli` needs its own Chromium build: `playwright-cli install-browser chromium`.

## Conventions

- Extension APIs: `import { browser, type Browser } from 'wxt/browser'`, promise style only (Firefox's `browser` has no callbacks). Types come from `@types/chrome`; methods with a callback overload need `mockResolved` from `tests/unit/helpers/mock.ts` in tests.
- Enums in the types (`contextMenus.ContextType`, `runtime.ContextType`) are passed as their string values, cast to the enum type: the enum objects don't exist at runtime in every browser.
- Storage: preferences in `storage.sync`. The customization preferences (badge scope, keep on screen, history limit, message times, density) are defined in `utils/preferences.ts` with their choices and defaults: read them with `getPreferences` / `parsePreferences` (an invalid value reads as the default, which keeps the behaviour without the setting), save only the key a control edits, and follow `storage.onChanged` in the views and the background. History, topic sync state, credentials, drafts, the inbox filter, pane widths, the Send disclosure state and the "More options" state (`sendOptionsOpen`) stay in `storage.local`. Queued attachments are Blobs in IndexedDB (`utils/stored-files.ts`); `storage.local` holds only their revision key (`storedFilesRevision`), which other views watch. Use separate pane width keys for the popup and tab. The synced divider freeze and Send remember preferences apply to both views. Keep credentials out of synced settings and tab addresses. Strip userinfo from parseable server URLs with the URL parser (`splitCredentials`). `getConfig` strips userinfo, queries and fragments from synced URLs and never uses credentials found there.
- No migrations: v1.0.0 is the first release, so code reads only the current storage formats. Rows, states or values in an older shape are dropped or ignored (validation still applies), not converted.
- The token and password are bound to the server origins approved on this device (`authOrigins` in `storage.local`): saving server URLs in this browser's settings approves them; a URL changed elsewhere (browser sync) gets no credentials until the user confirms in the settings. `getConfig` enforces it (`heldBackFrom`, empty token and credentials), so requests take their authentication from `getConfig`; `getStoredAuth` is for the settings form only. Authenticated requests refuse redirects (`redirect: 'error'`).
- Export and import (`utils/backup.ts`): the file holds the `storage.sync` keys only, never anything from `storage.local`. A new synced key goes into `BackupSettings` and `sanitizeSettings` (a unit test compares the keys with `ARCHITECTURE.md`'s storage table); a new local key stays out. Both directions go through `sanitizeSettings`, which uses the validators of the storage readers: never write a value from a file that a validator didn't return.
- The background is the only writer of the received messages, the read and deleted ids and the sync state, through one queue (`serialized` in `utils/history.ts`). The popup sends read and delete actions as messages (`utils/messages.ts`); it never saves those lists itself.
- Data keyed by topic is stored as a list (`[topic, value]` entries, or objects with a `topic` field) and read into a `Map`: topic names such as `__proto__` and `constructor` are valid in ntfy and break plain objects.
- HTTP errors read as `HTTP <status>: <text>` (`httpError`): the text is the string `error` field of ntfy's JSON body (read up to 4 KiB, control characters replaced, capped at 200 characters, shown as text only), else the status text, else nothing. Keep the `HTTP <status>` prefix: the receiver parses it and the sync status shows only the status code, never server-supplied text.
- Every request has a time limit (`TIMEOUTS` in `utils/ntfy.ts`). `isNoResponse` covers network errors and time limits. Select the fallback before publishing. A missing POST response leaves delivery uncertain.
- Header values are RFC 2047-encoded when they contain anything outside printable ASCII, including line breaks.
- Live messages come from ntfy's JSON stream (`openMessageStream`, GET `/<topics>/json`), not a WebSocket: a WebSocket can't carry headers, so it would need the credentials in the URL (`?auth=`), where browser error lists and proxy access logs record them. Never put credentials in a URL.
- Everything from the server is untrusted: messages go through `parseMessage` / `parseMessageJson` (types checked, unknown fields dropped) before they are stored, and again when the history is read. Limits include `MAX_MESSAGE_JSON` per event, `MAX_POLL_BYTES` per poll response, `MAX_POLL_EVENTS` per poll, and the `historyPerTopic` preference (50 to 500, default 100, never a free number) and `MAX_HISTORY_SIZE` for stored messages. Don't spread per-topic rows into a call (`Math.min(...rows)`): reduce over them. Only messages of subscribed or polled topics are stored. The stream is read one chunk at a time, after the lines before it are stored, so a flooding server is slowed down rather than queued. The Receive tab renders each message on its own (`renderMessageSafely`).
- Messages from the server are rendered with `textContent` only (Markdown through `utils/markdown.ts`, which builds nodes; bare URLs through its `linkify`); URLs from messages are opened, linked or copied only if `isHttpUrl`; images are previewed only from the ntfy server's own origin.
- Keyboard commands are declared in `wxt.config.ts` (`commands`) and handled in `utils/commands.ts`. `send-page` reuses `sendPage` in `utils/context-menu.ts` (same `getConfig`, `pickServer` and `showSendResult` as the menu's Page item) and has no default key. Verify both generated manifests and run `pnpm lint:firefox` when changing them. Chromium has no API to open its shortcut page or to hear about a changed shortcut; Firefox has `commands.openShortcutSettings` (137+).
- `requireInteraction` follows the `keepUrgentOnScreen` preference and is Chromium-only: the setting is hidden in Firefox (`import.meta.env.BROWSER`).
- Desktop notifications get buttons for a message's `view` actions only (`notificationButtons`); `http` and `broadcast` actions stay out, since they would make the browser send requests the publisher chose. Firefox shows no notification buttons.
- Vitest runs `tests/unit/*.test.ts`. The fake ntfy server in `tests/unit/helpers/fake-ntfy.ts` implements fetch and provides `FakeStream` to accept, refuse, deliver to or end subscriptions; it also accepts publishes (`published`) and holds delayed ones back (`scheduled`), refusing delays as ntfy does. Popup tests load the real `index.html` in happy-dom. `tests/unit/helpers/indexed-db.ts` installs a fresh `fake-indexeddb` per test with Node's `Blob` and `File` (Happy DOM's don't survive `structuredClone`) and queues files. The E2E build exposes `__ntfyAddPickedFiles` in the service worker to queue attachments. Playwright runs `tests/e2e/*.spec.ts`. The fixtures in `tests/e2e/fixtures.ts` provide `serviceWorker` (evaluate code in the background worker), `configure`, `notified` (desktop notifications recorded in the worker) and `openPopup`.

## Behaviour that is easy to break

- ntfy rejects a multi-topic subscription with 403 if any topic isn't readable: the receiver checks `/<topic>/auth` and subscribes to readable topics only.
- Each topic's sync state carries the configured main and fallback origins, a catch-up watermark (`since=<unix time>`, inclusive), and the id and time of every message at or after it. An unrelated server starts a fresh poll.
- Only a completed poll moves the watermark, never a live message: a live message newer than messages missed while disconnected must not let the next poll skip them. The sync state and the history are written in one storage write.
- Deletion sync is opt-in per topic (`syncDeletionTopics`). Match inbound deletions by server origin, topic and sequence ID. Treat configured main and fallback addresses as aliases. Every stored message carries the origin that delivered it (`serverOrigin`); a row without one is dropped on reading. Preserve replay order for events in the same second so a later publish can revive a sequence. Remote deletes require intent captured by the inbox action, a matching destination, a topic that remains opted in, and a verified message origin. A stale local-only action must stay local. Use `getConfig` for credentials and let ntfy enforce write access.
- Settings is five tabs (Server, Topics, Messages, Appearance, More; `showSettingsTab` in `settings.ts`). Panels are hidden, never removed: fields and staged topic settings keep their state. The status line (`#settings-status`) and the links stay outside the panels, so a message shows whatever the tab; a flow that ends with something to do on another tab switches there (an import with held-back credentials opens Server). `updateAttention` sets the gear's highlight and the tab marks together. The popup's settings view keeps a fixed height, or the toolbar popup would resize with each tab. Tests select a tab the way a user does (`selectSettingsTab` in the E2E tests): Playwright can't act on controls in a hidden panel, while happy-dom clicks them anyway.
- Commit server URLs and credentials only on **Save server settings**. Move userinfo to local credentials and strip queries and fragments. Other controls save only the preferences they edit. Validate topic names in settings and again before making requests. Verify the composer or context menu destination against current settings before publishing.
- Send defaults per topic (`topicSendDefaults`, `utils/send-defaults.ts`) apply only while the priority and tags are automatic: they follow the send topic until the user sets either by hand (`customPriorityTags`, kept in the draft), then stay through topic changes until the message is sent or reset. A change by hand updates the synced `priority` / `lastTags` only when the send topic has no defaults. The context menu and `send-page` send without priority or tags.
- More options (click URL, Markdown, delay) are headers (`X-Click`, `X-Markdown`, `X-Delay`, plus `X-Timezone` for a delivery time), validated before any request, sent with every attachment message and the ZIP, part of the draft and cleared after a send. Only the click URL and the delay's length are checked in the browser; the server's error text covers the rest. A delayed publish says "scheduled", keeps the toolbar popup open, and never points to the inbox for confirmation: the message isn't there until delivery.
- Dispatch draft saves from the edit handler so closing the popup cannot cancel a pending save timer. The background serializes saves and compares the revision before clearing the sent draft.
- Serialize attachment edits with the queue Web Lock in `utils/stored-files.ts`, and change the revision key after each edit. Check the selection limits before storing and verify files are still queued before each upload. Hold the composer publish lock across upload and cleanup. Keep queue edits available while the network request runs. Remove confirmed IDs without replacing the file list. Report post-publish cleanup failures separately from publish failures. Clear drafts and attachments (and a leftover `storedFiles` key of earlier builds) on `runtime.onStartup`, including after a browser crash.
- Local deletes remove rows and save replay-suppression IDs in one write. Polls read NDJSON incrementally, keeping a bounded batch. If the scan limit is reached, continue from the stored prefix and report the gap.
- Updates: a `message` replaces stored rows of the same topic and sequence (`sequenceOf`; without `sequence_id` that is the id, so those never collide) from the same server (main and fallback are aliases, an unrelated server's rows stay), on every topic, deletion sync or not. The later version wins: later time, or in the same second the later position in a poll; a same-second row a poll didn't return arrived live after it, and a live event is later than rows stored before it. An older version arriving late is marked seen but neither stored nor notified. Within a poll only the last publish of a sequence counts, even if that one isn't stored (deleted here), so an older version can't come back in its place. A poll keeps the position of every saved row's publish outside its bounded tail, on every topic (`positionOnly`: position without content, never stored). The update is a new id: unread, notified per the topic rule. A locally deleted id stays suppressed, but an update of a locally deleted message (a new id) appears. Deletion sync still revives a sequence republished after a delete.
- Desktop notifications are dismissed (`clearNotifications`, id = message id) when a message is marked read, deleted in the inbox, removed by a synced deletion or replaced by an update: the background clears them after applying the action (`handlePopupRequest`, `deleteReceivedMessages`, the receiver's `onRemoved` from the ids `recordEvents` returns). A failed dismissal never fails the action; `history.ts` doesn't use the notifications API. Creating and dismissing share one queue in `utils/notifications.ts`, and an id dismissed in this run of the background is never shown afterwards, so a dismissal can't be overtaken by a notification still being prepared.
- The history limit is read inside the history queue on every write. A changed limit is applied at once by `applyHistoryLimit` in the same queue (the background's `storage.onChanged`); raising it must never bring messages back.
- The toolbar badge counts per the `badgeScope` preference (`updateUnreadBadge`); the inbox's per-topic counts always cover every topic. The badge is recomputed when the scope or a topic's rule changes.
- A history trim sets `retainedFrom` in the topic's sync state (newest dropped time); `recordEvents` doesn't store older messages again. Keep it separate from the catch-up watermark.
- History is ordered by server time before the per-topic limit applies; a connect() that an await made stale (settings changed meanwhile) stops; a subscription refused before it opened discards the cached read-access check.
- Image previews only load the server's attachment route (`/file/<name>`, no query): other same-origin URLs can be API calls (ntfy publishes on GET).
- A topic's first sync is silent. Later catch-up only notifies about newly retained history and summarizes bursts across the whole pass. An empty first poll seeds a server timestamp with overlap when the Date header is visible. Otherwise later polls use a duration based on elapsed time. Deletion replay keeps relevant older events outside the ordinary batch and marks completion only when the scan is complete and server truncation can be ruled out.
- An import replaces every synced key in one `storage.sync.set`, under the settings lock, after the confirmation and a check that the settings didn't change since the preview. It never writes credentials and never approves a server: `importSettings` records the servers configured before the import as `authOrigins` when no approvals exist yet (whether or not a token or password is stored: one saved later is held back from the imported server too), under `withAuthOriginsLock`, the lock `getConfig` takes and re-reads under before it records first-time approvals (never call `getConfig` while holding it), so `getConfig`'s first-time approval can't approve an imported server. The file dialog and the confirmation need a page that stays open: the toolbar popup hands import (and, in Firefox, export) to the extension tab.
- Chrome stops an idle service worker after 30 s, and data arriving on a fetch stream doesn't count as activity (tested: stopped after ~30 s with data every 20 s), but an extension API call does: the receiver calls `runtime.getPlatformInfo` every 20 s while subscribed (tested: alive for 8+ minutes). A stream has no close event when the connection dies silently, so it is given up after `STREAM_IDLE_TIMEOUT` without data (ntfy's keepalive is 45 s by default).
